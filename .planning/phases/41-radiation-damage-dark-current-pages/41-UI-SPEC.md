# Phase 41 — UI Design Contract

> Visual and interaction contract for the Radiation Damage + Dark Current pages. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **Framing note:** Streamlit target, not React/shadcn. shadcn gate is **not applicable** (no `components.json`, no `package.json` in this repo — confirmed by direct filesystem check). This phase **inherits Phase 38's Design System, Spacing Scale, Typography, and Color tokens wholesale, by reference** — they are not re-derived here. Only phase-specific additions (data-viz trace palette, two new plot contracts, two new widget layouts, partial-failure copy) are declared below. Any value not explicitly overridden here defers to `.planning/phases/38-streamlit-shell-device-config-page/38-UI-SPEC.md`.
>
> **Critical precedent note:** `41-RESEARCH.md` contains a **Decision Addendum** (near the end of the file) that supersedes its own earlier bias-sweep sections for the dark current page. The dark current page sweeps **temperature** (`T_min`/`T_max`/`n_temperatures`) at a **fixed operating bias**, via `petringa.ParametricSweep`, NOT a bias sweep. This UI-SPEC reflects the addendum, not the earlier (superseded) bias-sweep material in the same research file.

## Typography

**Inherited verbatim from Phase 38.** Exactly 4 sizes (14, 16, 28, 36), exactly 2 weights (regular, semibold). **`st.header` remains the ONLY section-heading primitive** — do not introduce `st.subheader` for "Inputs"/"Results" sub-groupings on either new page; use `st.header` if a sub-heading is needed, or rely on widget grouping (`st.columns`, `st.expander` labels) without a heading at all, to avoid adding a 5th size to the scale.

| Role             | Streamlit primitive                                         | Size | Weight            | Line Height   |
| ---------------- | ----------------------------------------------------------- | ---- | ----------------- | ------------- |
| Page title       | `st.title("Radiation Damage")` / `st.title("Dark Current")` | 36px | semibold          | ~1.2 (native) |
| Body / label     | widget labels, `st.write`                                   | 16px | regular           | ~1.6 (native) |
| Caption / helper | `st.caption(...)` — e.g. numeric readouts below the chart   | 14px | regular           | ~1.5 (native) |
| Numeric readout  | `st.json`/`st.code` (monospace)                             | 14px | regular monospace | ~1.5 (native) |

No `st.header`/`st.subheader` is required on either page this phase — each page has exactly one `st.title` and no sub-sections deep enough to warrant a second heading level. If the executor finds a sub-heading genuinely necessary (e.g. separating "Fluence Range" from "Physical Conditions" widget groups), use `st.header` per the Phase 38 contract — never `st.subheader`.

## Color

**Inherited verbatim from Phase 38** for UI chrome (60/30/10 split, `primaryColor = #1F6FEB`, warning amber, error red). Restated here for this phase's specific usage, plus a **new data-visualization trace palette** required because this is the first phase with multi-trace overlaid plots.

### UI chrome (inherited, not re-derived)

| Role               | Value              | Usage in this phase                                                                                                                                                                                            |
| ------------------ | ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Dominant (60%)     | `#FFFFFF`          | Main panel background, plot canvas surface (both pages)                                                                                                                                                        |
| Secondary (30%)    | `#F0F2F6`          | Sidebar (unchanged — device config only); `st.expander` collapsed background (Advanced trap-parameter overrides on dark current page)                                                                          |
| Accent (10%)       | `#1F6FEB`          | Reserved for: the "Run simulation" button (both pages), the active nav indicator for Radiation Damage / Dark Current in the sidebar nav list. **Not** used for plot trace colors — see data-viz palette below. |
| Warning (semantic) | `st.warning` amber | The persistent kappa-data-blocked banner (radiation damage page, unconditional); the truncated/partial-result info banners (both pages, conditional on partial failure)                                        |
| Error (semantic)   | `st.error` red     | `try/except RuntimeError` failure message (both pages, if the Run call raises outright)                                                                                                                        |

### Data-visualization trace palette (NEW this phase — explicitly distinct from the 10% UI accent)

Multi-trace plots must use a **qualitative data-viz palette**, not the UI's `primaryColor`. This keeps the 10% accent budget meaningful (reserved for the Run button and nav indicator only) and gives each physical quantity a stable, distinguishable color across both new plots and any future overlay page (Phase 42 batch sweep will reuse this palette).

| Trace role                                    | Color (hex)                                                                                                                                                  | Line style                    | Used on               |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------- | --------------------- |
| Primary result (CCE vs fluence; single trace) | `#1F6FEB` (same as accent — acceptable for a **single-trace** plot, no ambiguity risk)                                                                       | solid, `mode="lines+markers"` | Radiation Damage page |
| CCE = 1.0 reference line                      | `#9AA0A6` (neutral gray)                                                                                                                                     | dashed, `opacity=0.5`         | Radiation Damage page |
| I_total                                       | `#1A1A1A` (near-black, matches Phase 38 text color — reads as "the headline number")                                                                         | solid, `lines+markers`        | Dark Current page     |
| I_SRH (bulk)                                  | `#1F6FEB` (blue)                                                                                                                                             | solid, `lines+markers`        | Dark Current page     |
| I_TAT (effective, trap-assisted)              | `#D32F2F` (red — reused from the semantic error red family since TAT values are frequently negative/generation-sign, giving a visual "handle with care" cue) | solid, `lines+markers`        | Dark Current page     |
| I_SRV (surface)                               | `#2E7D32` (green — new, data-viz-only color, not used elsewhere in the UI chrome)                                                                            | solid, `lines+markers`        | Dark Current page     |

**Rule:** the 4-trace dark current palette is fixed and always applied in this order (I_total, I_SRH, I_TAT, I_SRV) regardless of which traces are zero-guarded out (Pitfall 3) — a hidden trace does not shift the remaining colors, so the mapping stays memorable across re-runs with different parameter values.

There are **no destructive actions** in this phase (no delete/overwrite-with-loss operations — Run simply replaces the cached `SimResult`/`list[SimResult]` in `session_state`, matching Phase 38/39's precedent), so no destructive color beyond the existing semantic error red is introduced.

**Discretion Resolved (from RESEARCH.md Assumption A5, Open Question #3):** `proton_energy_MeV` is a `st.selectbox` restricted to the 4 real NIEL-hardness-table keys `{30, 62, 70, 150}` — **not** a free `number_input`. Rationale: this is consistent with the honesty theme already established by the kappa warning banner — presenting a free-entry field would imply false numerical precision for energies the underlying `np.interp` table does not actually tabulate. `62` MeV is the default (index 1), matching a commonly-used clinical/reference proton energy.

## Plot Contract

### Radiation Damage — CCE vs Fluence (`build_damage_figure`)

| Property       | Value                                                                                                                |
| -------------- | -------------------------------------------------------------------------------------------------------------------- |
| Trace          | single `go.Scatter`, `mode="lines+markers"`, color `#1F6FEB`                                                         |
| Reference line | `fig.add_hline(y=1.0, line_dash="dash", line_color="#9AA0A6", opacity=0.5)`                                          |
| X-axis         | `xaxis_type="log"`, title `"Proton Fluence (p/cm²)"`                                                                 |
| Y-axis         | title `"Charge Collection Efficiency"`, `yaxis_range=[0, 1.1]`                                                       |
| Title          | `"CCE vs Proton Fluence"`                                                                                            |
| NaN tolerance  | no special handling required — Plotly renders a `NaN` y-value as a gap in the line automatically; do not `.dropna()` |

### Dark Current — Decomposition vs Temperature (`build_dark_current_figure`)

**Supersedes the bias-axis code example earlier in `41-RESEARCH.md`** — the x-axis is temperature, per the Decision Addendum.

| Property                  | Value                                                                                                                                                                                                                                                                                                                                                     |
| ------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Traces                    | 4 overlaid `go.Scatter`, `mode="lines+markers"`, per the data-viz palette table above, in fixed order: I_total, I_SRH, I_TAT, I_SRV                                                                                                                                                                                                                       |
| Zero/negative-guard       | `I = np.abs(np.asarray(values))`; only add a trace if `np.any(I > 0)` — mirrors `petringa.core.dark_current.plot_dark_current_decomposition`'s existing `abs()` + zero-guard pattern (see RESEARCH.md Pitfall 3). A guarded-out trace (e.g. all-zero I_SRV at default `S_n`/`S_p`) is simply omitted from the legend, not shown as an empty/broken trace. |
| X-axis                    | linear (NOT log — temperature range is narrow, e.g. 250-400K, no benefit to log scale), title `"Temperature (K)"`                                                                                                                                                                                                                                         |
| Y-axis                    | `yaxis_type="log"`, title `"Absolute Dark Current (A)"` (avoid magnitude-bar notation in the axis title string entirely — it introduces literal pipe characters that break Markdown table parsing in this spec and are unnecessary since the axis is already log-scaled)                                                                                  |
| Title                     | `"Dark Current Decomposition vs Temperature"`                                                                                                                                                                                                                                                                                                             |
| Data shape note           | input is a `list[SimResult]` (one per temperature, from `ParametricSweep`), not a single `SimResult` — the builder must extract one operating-point value per temperature from each per-T result (e.g. `result.y[0]` at the fixed bias) to build the `x=temperatures`, `y=I_total/I_SRH/I_TAT/I_SRV` arrays of length `n_temperatures`                    |
| Partial-failure tolerance | a per-temperature entry that failed/returned no data is simply omitted from all 4 arrays at that index (see Copywriting Contract's per-temperature truncation banner) — do not attempt to interpolate or fabricate a missing point                                                                                                                        |
